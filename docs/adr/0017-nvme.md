# ADR 0017: NVMe driver

- Status: accepted
- Date: 2026-11-10

## Context

The installer (ADR 0016) could only write to VirtIO disks, which exist
only in virtual machines. Most current computers have NVMe disks. NVMe is
also the simplest real storage interface to drive: a small register
block and queues in memory, publicly specified.

## Decision

A native driver, `kernel/src/drivers/nvme.rs`, written from the NVM
Express Base Specification, with the same shape and the same deliberate
limits as the VirtIO block driver:

- the first controller found (PCI class 01:08:02) and its namespace 1;
- one admin and one I/O queue pair of 16 entries, one command at a time;
- data goes through one bounce page, so a command carries at most 4 KiB
  and never needs a PRP list; larger requests are split;
- completions are polled, yielding the CPU in between; no interrupts;
- every write request ends with a Flush command, because the block
  layer promises that written data is on the medium;
- only namespaces formatted with 512-byte sectors.

The disk is registered as `nvme0n1`; its partitions are `nvme0n1p1`, ...
(a `p` separates the number when the disk name ends in a digit).

## What works

`install-to-nvme` in QEMU: the controller is found and identified, the
system installs itself onto the disk (tens of thousands of commands),
files are written to the new data partition, the machine restarts from
the NVMe disk alone, and the files compare equal. The host then checks
the partition table, the boot files and the ext2 filesystem with
independent tools.

A bug this test found during development: the driver read a completion
entry's command identifier before its status word, and could pair a
stale identifier with a fresh phase bit while the device was writing the
entry. The status word is now read first.

## Limitations

- **Never run on real hardware.** QEMU's controller is forgiving; real
  controllers differ in timing and optional features. Until someone
  tries it on a machine with nothing to lose, treat it as untested there.
- Slow by design: 4 KiB per command, a flush per write, polling at the
  scheduler's pace. No measurements have been made.
- One controller, one namespace, no 4096-byte-sector namespaces, no
  hot-plug, no power management, no shutdown notification to the
  controller (it is told nothing before power-off; the flushes are what
  protects data).
- A command that times out leaves the driver unusable; there is no
  controller reset and retry.
- On a real machine the keyboard is usually USB, for which there is no
  driver, so even where the disk works the system may not be operable.

## Alternatives considered

- **Reusing Linux's NVMe driver through LinuxKPI.** It depends on the
  Linux block layer, blk-mq, DMA and interrupt infrastructure — far more
  than the layer provides. A native driver of this size is less work and
  less risk.
- **AHCI first.** SATA is more complicated to drive and less common in
  new machines.
