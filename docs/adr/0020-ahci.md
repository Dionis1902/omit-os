# ADR 0020: AHCI driver (SATA disks)

- Status: accepted
- Date: 2026-11-10

## Context

After VirtIO (ADR 0009) and NVMe (ADR 0017) one common kind of disk was
still out of reach: SATA. It is what QEMU, VirtualBox and VMware give a
virtual machine unless told otherwise, so trying the installer meant
configuring a special disk first; and it is what many real machines
still have.

## Decision

A native driver, `kernel/src/drivers/ahci.rs`, written from the Serial
ATA AHCI specification and the ATA command set, with the same shape and
limits as the other storage drivers:

- the first AHCI controller; each port with an ATA disk attached;
- the controller is **not reset** — the firmware has just used it — but
  each such port is stopped, pointed at the driver's memory and started
  again; a firmware hand-off is requested where the controller has one;
- one command at a time per disk, in command slot 0, with one 4 KiB
  bounce page; polling; a `FLUSH CACHE EXT` after every write request;
- `READ DMA EXT` / `WRITE DMA EXT` only, so 48-bit addressing is
  required; 512-byte logical sectors only.

Disks are named by port — port 0 is `sda`, port 2 is `sdc` — so a disk
keeps its name whatever else is attached. (Linux numbers disks in the
order it finds them; here determinism was worth more than familiarity,
since a wrong name given to `install` erases a disk.)

## What works

`install-to-sata` in QEMU: a blank SATA disk on port 2 is found and
identified, the system installs itself onto it, files are written to
the new data partition, the machine restarts from that disk alone, and
the files compare equal; the host then checks the partition table, the
boot files and the ext2 filesystem with independent tools. In the test
runs that boot from a disk image, that image is itself a SATA disk on
port 0, read by the driver at start-up (identify, first sector,
partition table).

## Limitations

- **Never run on real hardware**; tested against QEMU's ICH9 emulation
  only.
- No ATAPI devices (CD/DVD drives are reported and skipped), no port
  multipliers, no hot-plug, no native command queuing, no power
  management, no SMART.
- Slow by design: 4 KiB per command, a flush per write, polling. No
  measurements have been made.
- A command that times out is not recovered from (no port reset).
- A live system started from a disk image on a SATA port now sees that
  image as a disk, so `install` can be pointed at the medium the system
  was started from. That works — the running system is in memory — but
  erases the medium. `install` names nothing by default and requires
  `--erase`; nothing else guards against it. (A USB stick is not
  visible: there is no USB storage driver.)

## Alternatives considered

- **Resetting the controller** (`GHC.HR`), as larger systems do. It
  discards firmware-programmed values some controllers do not restore,
  and requires re-detecting links; taking over port by port is less
  code and less risk.
- **Legacy IDE mode.** Not available on current chipsets.
